# ADR-0004: The Android app

Status: Accepted. Built: the spike on the test phone, the core's Android build (`android/build-core.sh`) and streaming mode (`peil live`), the normalizer for the app's raw lines (the `android` source), and a first app: the session service, the saved feeds with their retention and "delete all", the core as a process, and the ring. Not yet built: release signing, the in-app license notices, restarting a core that stopped, the heading sensor, raw GNSS measurements, the camera and find mode, the laptop link, and the CI build and its checks. Amends ADR-0001 sections 1 and 3 and its consequences, and ADR-0002 sections 1 and 3.

## Context

The first releases answer the founding question (ADR-0001) for the space around a vehicle while it drives, with hardware already at hand: an Android phone, a laptop that runs Kismet, and small Linux computers as extra receivers. The phone has its own Wi-Fi and BLE radios, GNSS with raw measurements, a compass, a camera and a screen fit for a car. It can answer part of the question with nothing else attached, and it is the display when the laptop is there too.

ADR-0001 assumes a Linux computer reading Kismet, rtl_433 and gpsd as separate processes, with "the CLI first, then a HUD" as front ends. A phone changes three things: what the sensor tier is, how the core runs, and where the session clock comes from. The judge must stay one deterministic implementation (ADR-0001 section 4), whatever runs it.

## Decision

1. **A Kotlin app in `android/` in this repository**, built with Gradle, sideloaded as a signed APK; it isn't published to an app store. Releases are signed with one key (APK Signature Scheme v3), kept offline and in a GitHub environment that only release tags can use, never in the repository; the certificate's SHA-256 fingerprint is pinned in the repository, the signing step fails on any other, and each release's notes print it. The version code is `major * 10000 + minor * 100 + patch`. Its application ID is `io.github.erickramer42.peil`, since Android shows it to the user (ADR-0003 section 1); its code namespace is `io.github.erickramer42.sensio` (ADR-0003 section 2). It is Peil's first HUD (ADR-0001 section 3). It needs Android 12 (API 31) or later and targets Android 16 (API 36).

2. **The app is fully functional alone.** The phone's radios, GNSS and sensors, the judge and the display all run on the phone. A laptop with Kismet, and receivers behind it, add observations when they're connected; nothing in the app waits for them. The vehicle's own data (speed and engine state from Havne's `havne-cli`) comes only through the laptop, since `havne-cli` doesn't run on Android; alone, the app judges without it. Havne's own Android app reads the car over Bluetooth on the same phone, but using it would mean two apps and a contract between them, and its relay passes raw adapter bytes only in developer mode; that stays an option for a later ADR.

3. **On the phone, the sensor tier is Android itself.** The app reads the operating system's scan results and sensor readings: Wi-Fi scan results, BLE scan results, `LocationManager` fixes with raw GNSS measurements, and the rotation-vector sensor for heading. It captures nothing below those interfaces and uses no Google Play services: they are proprietary, and fused location hides the raw GNSS measurements that interference detection needs.

4. **Kotlin collects and displays; the core decides.** The app writes each scan result and sensor reading as a raw JSON line with its session time, and passes the lines to the core. The core runs as a separate process inside the app: the `peil` binary built for `aarch64-linux-android`, packaged in the APK as a native library so that Android installs it executable, started by the app and spoken to in JSON lines over stdin and stdout. Normalizing, merging sources, the judge and find mode's bearing estimate all run in Rust, so the phone's verdicts are the ones `peil judge` gives on Linux for the same events, and the workspace keeps forbidding `unsafe`. The pipe is framed the same way in both directions: a first line naming its schema, a `type` on every line, and a last line with a reason and totals. On a live session the app never blocks on a slow core: it drops lines and writes the count in-band. The live verdict at a time t is the judge over the events that arrived by t; the app records each time it asks the core to judge, so replaying the session through the same rules reproduces every verdict the user saw, at the moment it was shown. A lookback window, where a rule has one, is a parameter of that rule, not a property of the live loop.

   The alternatives weighed:
   - **A JNI bridge** (the `jni` crate) calls the core in-process. Its exported functions need `#[no_mangle]`, an exception to the workspace's ban on `unsafe`, and a crash in the core takes the app down with it.
   - **UniFFI** generates the Kotlin side, but it is MPL-2.0, outside `deny.toml`'s allowlist, and is an in-process bridge too.
   - **The judge rewritten in Kotlin** would be a second implementation of every rule, free to drift from the first.

5. **The phone keeps its own session clock** while the app runs alone (ADR-0002 section 3 assumes PPS, which a phone doesn't expose). The app stamps every line's arrival with `SystemClock.elapsedRealtimeNanos()` (`CLOCK_BOOTTIME`), which keeps counting while the phone sleeps; `System.nanoTime()` and Rust's `Instant` stop, so the core on the phone reads no clock of its own. Those stamps map to UTC nanoseconds through GNSS time while there's a fix, and through the system clock otherwise. The sync state goes with the session, so a session on a poorly synced clock is flagged, as ADR-0002 requires. The growing difference between `elapsedRealtime` and `uptimeMillis` is the time the phone has slept; a rise of a second or more is written into the session as lost coverage.

6. **The link to the laptop is USB tethering only.** The app listens only on the tethering interface, never on Wi-Fi or mobile data. On the laptop, a `peil` process reads Kismet (ADR-0001 section 1), finds the phone as the gateway of its tethering interface, and sends Kismet's output as JSON lines over HTTP, each line with the laptop's session time. The phone measures the offset between the two clocks with timed round trips over the same link, and maps the laptop's times onto its own with that offset and its uncertainty. Any app on the phone and any process on the laptop could reach that listener and feed it false observations, so it opens only while the laptop link is turned on in the app, takes one client at a time, and requires a pairing code the app shows, given to the laptop's `peil`. The code is new each time the link is turned on, and three wrong codes close the listener until it's turned on again. `adb` is for installing the app and running instrumented tests; the app never depends on it.

7. **Running in the background, and personal data on the phone.** A session runs in a foreground service of type `location`, started when the user starts a session with the app open (Android refuses to start one from the background), with a partial wake lock held from the session's start to its end: without the lock the CPU sleeps with the screen off even while the service runs. The app declares only the permissions a feature uses: fine location, Bluetooth scanning, nearby Wi-Fi devices, the camera, `FOREGROUND_SERVICE` and `FOREGROUND_SERVICE_LOCATION`, `WAKE_LOCK`, notifications (if refused, the service still runs), and network access, which Android requires for any socket, the tethering link included. Bluetooth scanning is declared without `neverForLocation`: with that flag, Android filters some beacons out of the results, the devices Peil looks for. The service isn't exported. Backups and device-to-device transfer are off (`allowBackup` false, and data-extraction rules that exclude every domain). It asks for no storage access. From the first session, it writes every source's raw lines as received, the laptop's included, with their arrival times and the judging times, to its private storage: the raw half of ADR-0002's recording, which the recorder later completes with its manifest. Those files hold other people's identifiers and the user's movements (ADR-0002 section 5): they stay on the phone, are deleted after a retention period the user sets, and can all be deleted at once from the app. It never writes camera frames: the camera feeds a live preview and in-memory analysis for find mode's overlay, with no photo or video capture, and no frame is stored or sent anywhere (ADR-0002 section 5).

   Amended 2026-11-07: reading Wi-Fi scan results and asking for a scan also need `ACCESS_WIFI_STATE` and `CHANGE_WIFI_STATE`, and Android 12 and later grant fine location only when coarse location is asked for with it, so the app declares both. The camera and network permissions are declared once a feature uses them (find mode, the laptop link).

8. **Licensing: MIT as far as the platform allows.** The app's own code is MIT, like the workspace, and the core inside it is held to `deny.toml`. The app uses Android's platform APIs directly (its views and canvas for the display, Camera2 for the camera, its own threads) rather than AndroidX, Jetpack Compose, CameraX or kotlinx coroutines, which are Apache-2.0 and would ship inside the APK. The only third-party libraries in the APK are the Kotlin standard library and the annotations it depends on (`org.jetbrains:annotations`), both Apache-2.0, which every Kotlin program ships; the app shows their license text, and THIRD_PARTY_NOTICES.md lists them once the APK exists. No Google Play services, analytics, crash reporting, ads or network libraries. Another library in the APK needs this ADR amended. Build and test tools that never ship in the APK (Gradle, the Android Gradle plugin, a test framework) are outside this rule.

9. **CI builds the app:** the core for `aarch64-linux-android` with the Android NDK, the APK, and the app's JVM unit tests. Because cargo-deny can't see Gradle, a check lists the libraries packaged in the APK and fails on any beyond the Kotlin standard library and its annotations; another check reads the merged manifest (minimum SDK, the permission list, the service and its flags, backups off); and the Gradle wrapper's checksum is validated. Actions are pinned as for the Rust jobs.

## Consequences

- Android becomes a primary platform beside Linux, and the sensor tier on the phone is the operating system rather than a separate program; ADR-0001 sections 1 and 3 and its Linux consequence, and ADR-0002 section 3, take dated amendments pointing here when this ADR is accepted.
- The event schema needs Wi-Fi event kinds and a receiver on every observation, and `peil` needs a mode that reads raw lines and writes live verdicts as a stream; both come before the app can judge anything.
- The Android build needs the NDK and the Rust target `aarch64-linux-android`.
- Packaging an executable as a native library depends on Android extracting native libraries to disk and allowing them to run. The Android Gradle plugin leaves them inside the APK unless legacy packaging is turned on, and the binary must be aligned for 16 KB memory pages. If this doesn't work, or a later Android version stops allowing it, the fallback is the JNI bridge and its `unsafe` exception, in a new ADR.
- Before the app is built, a spike on the test phone confirms or refutes each assumption here, recorded with its evidence: the core running from the native library directory; a listener on the tethering interface on Android 16, and the laptop finding it as its gateway; the `location` foreground service type with a wake lock keeping scans going with the screen off; the core's process surviving a long screen-off session (Android 12 and later's phantom process killer stops child processes beyond 32 across all apps, or ones using much CPU in the background); BLE scanning with the screen off through a scan filter; the Wi-Fi scan rate with throttling on and off; raw GNSS measurements and their automatic-gain-control level through `GnssMeasurementsEvent.getGnssAutomaticGainControls()`, which replaces the deprecated per-measurement level. If the core's process can't survive, the JNI fallback applies. A phone on USB power never sleeps, so sleep is tested with the phone alone.
- Without its foreground service, Android 14 and later may freeze the app, the core's process with it; battery saver can still stop the service.
- If the core's process dies, the app restarts it and shows the gap as lost coverage.
- Android limits a foreground app to four Wi-Fi scans every two minutes unless "Wi-Fi scan throttling" is turned off in Developer options, and Wi-Fi scan results list access points only. The app shows which state it runs in; monitor-mode Wi-Fi comes from Kismet on the laptop.
- Android pauses BLE scans that have no scan filter while the screen is off (a wake lock doesn't help), allows five scan starts per 30 seconds, and downgrades an unfiltered scan running more than 30 minutes to opportunistic, which only sees results other apps asked for. The app scans with a filter, keeps one scan running rather than restarting it, and shows any scan it lost as lost coverage. Amended 2026-11-06, from the spike on the test phone: a filter that matches everything is paused with the screen off just as no filter is (zero results after the first screen-off minute), while filters on specific manufacturer IDs and tracker service UUIDs keep scanning, at roughly a tenth of the screen-on rate after a few minutes. So the app scans with a match-everything filter while the screen is on and switches to the specific filters while it's off, recording the screen-off minutes as reduced coverage (only the listed manufacturers and services). In the car the phone is the display with its screen on.
- Because raw lines are kept from the first session, every drive can be replayed through a newer rule once replay exists, the reason ADR-0002 keeps raw recordings; the recorder imports sessions written before it.
- Platform APIs cost more code than AndroidX would: Camera2's session handling, hand-drawn views, and handling Android version differences without compatibility libraries. The display Peil needs (a list, the radar ring, the find-mode wedge over a camera preview) is small enough to draw by hand. Kotlin's standard library is the one Apache-2.0 part of the APK; an app in Java would ship none, at the cost of Kotlin's null safety and sealed classes.
- The same core binary and rules run on the phone and on Linux, so the golden verdicts and the property tests cover the phone's judge too.
